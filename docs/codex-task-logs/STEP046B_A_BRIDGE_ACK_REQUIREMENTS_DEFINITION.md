# STEP046B-A - Bridge ACK Requirements Definition

Date: 2026-06-07

Status: COMPLETE / Planning Only

## Scope

STEP046B-A defines Bridge ACK requirements only. No source code, Android logic, ESP32 firmware, Raspberry Pi gateway service, or routing logic was modified.

## Problem

Physical messaging succeeds, but Bridge ACK display/reliability is inconsistent:

- Android may show `Bridge ACK: No response`.
- Android may show raw JSON instead of a user-readable ACK state.
- The destination still receives the message.

This means the current issue is ACK interpretation/display reliability, not proven LoRa message delivery failure.

## Bridge ACK Definition

Bridge ACK is the user-facing confirmation that a message sent from an Android phone through its local ESP32 bridge has been acknowledged by the final destination node.

Bridge ACK must not mean only that Android wrote bytes to Bluetooth, that the local ESP32 accepted the message, or that an intermediate gateway forwarded the packet.

## ACK Source Decision

Recommended authoritative source:

- Destination node ACK.

Diagnostic-only sources:

- Forwarding gateway ACK.
- Hop-by-hop ACK.

Rationale: forwarding and hop ACKs prove relay progress but do not prove destination delivery. Since current messages can succeed while the UI reports `No response`, the safest design is to separate final delivery ACK from internal forwarding diagnostics.

## Safest ACK Design

Use a two-tier ACK model:

- Delivery ACK: generated by the final destination node after it accepts or delivers the message to its local phone/access side. This is the only ACK that should set the user-facing Bridge ACK state to `Delivered`.
- Forwarding / Hop ACK: optional internal diagnostics generated by gateways or relays. These can update route/debug logs but must not be displayed as final delivery.

Do not add Bluetooth as a node-to-node MANET transport. Bluetooth remains Android phone-to-local ESP32 access only; LoRa remains the MANET backbone.

Do not change routing core for STEP046B unless a later implementation task explicitly approves it.

## ACK Packet Format

ACK packets must correlate to the original message with `ackFor`.

Canonical BT-MANET JSON ACK over Android phone-node Bluetooth access:

```json
{
  "protocolVersion": "BT-MANET-1.0",
  "packetType": "ACK",
  "packetId": "ACK-<ackFor>-<ackSource>-<timestamp>",
  "sourceNode": "<ackSource>",
  "destinationNode": "<originalSourceNode>",
  "payload": {
    "ackVersion": 1,
    "ackType": "DELIVERY",
    "ackFor": "<originalMessagePacketId>",
    "ackStatus": "DELIVERED",
    "originNode": "<originalSourceNode>",
    "finalDestinationNode": "<originalDestinationNode>",
    "ackSource": "<destinationNode>",
    "reason": "",
    "route": ["nodeA1", "nodeA2"]
  },
  "hopPath": "<ackSource>><originalSourceNode>",
  "hopCount": 0,
  "ttl": 6,
  "previousHop": "<ackSource>",
  "retryCount": 0,
  "timestamp": 0,
  "status": "ACK",
  "checksum": "CHECKSUM_PLACEHOLDER"
}
```

Compact `BT1` LoRa ACK form, if carried over the LoRa backbone:

```text
BT1|ACK-<ackFor>-<ackSource>-<timestamp>|<ackSource>|<originalSourceNode>|{"ackVersion":1,"ackType":"DELIVERY","ackFor":"<originalMessagePacketId>","ackStatus":"DELIVERED","originNode":"<originalSourceNode>","finalDestinationNode":"<originalDestinationNode>","ackSource":"<destinationNode>","reason":"","route":["nodeA1","nodeA2"]}|<hopPath>|<hopCount>|<ttl>|<previousHop>|<checksum>
```

Allowed `ackType` values:

- `DELIVERY`: final destination-node ACK. User-facing.
- `FORWARD`: forwarding gateway or relay ACK. Diagnostics only.
- `HOP`: link-local hop ACK. Diagnostics only.

Allowed `ackStatus` values:

- `DELIVERED`
- `FORWARDED`
- `ACCEPTED`
- `DUPLICATE`
- `FAILED`
- `UNKNOWN`

## Timeout And Retry Rules

User-facing timeout:

- Android waits up to 12 seconds for a matching `DELIVERY` ACK where `ackFor` equals the outgoing message packet ID.
- During the wait, display `Bridge ACK: Pending`.
- If no matching delivery ACK arrives by 12 seconds, display `Bridge ACK: Delivery ACK pending` or `Bridge ACK: Unknown`, not `Message failed`.

Retry rules for STEP046B implementation:

- Do not automatically retransmit the original MESSAGE in STEP046B unless explicitly approved later; retransmission can create duplicates and may interact with duplicate suppression.
- Retry only ACK read/parsing/polling on the Android Bluetooth socket during the timeout window.
- Ignore unmatched ACK packets for the current message display, but keep them in diagnostics.
- Parse all inbound JSON lines before declaring no ACK.
- Never show raw JSON as the primary Bridge ACK display.

Future optional retry rule:

- A later task may add an explicit `ACK_STATUS` query by `ackFor`, but this is out of scope for STEP046B-A and not implemented here.

## Android UI Display Rules

Display states:

- `Bridge ACK: Pending` while waiting for a matching final delivery ACK.
- `Bridge ACK: Delivered to <nodeId>` when `ackType=DELIVERY` and `ackStatus=DELIVERED`.
- `Bridge ACK: Forwarded via <nodeId>` only in diagnostics for `FORWARD` ACKs.
- `Bridge ACK: Hop accepted by <nodeId>` only in diagnostics for `HOP` ACKs.
- `Bridge ACK: Delivery ACK pending` or `Bridge ACK: Unknown` when the timeout expires without a matching delivery ACK.
- `Bridge ACK: Failed - <reason>` only when a correlated final ACK explicitly reports `FAILED`.

UI must not:

- Show raw JSON in the user-facing Bridge ACK line.
- Treat forwarding ACK as final delivery.
- Treat ACK timeout as proof that message delivery failed.
- Rename Bluetooth into a MANET transport.

## STEP046B Implementation Acceptance Criteria

Implementation can be accepted only when:

1. Android sends a message and displays `Bridge ACK: Pending` while waiting for the matching ACK.
2. A final destination-node delivery ACK updates the message to `Bridge ACK: Delivered to <nodeId>`.
3. Gateway/forwarding ACKs, if present, appear only as diagnostics and do not mark the message delivered.
4. Raw ACK JSON never appears in the primary Chat/Bridge ACK UI.
5. ACK matching uses `ackFor == original packetId`.
6. Unmatched ACK packets do not update the wrong message.
7. Timeout without final ACK displays `Delivery ACK pending` or `Unknown`, not a false failure.
8. Message delivery remains non-regressed for `PhoneA -> nodeA2` and `nodeA2 -> PhoneA`.
9. Gateway disappearance detection and gateway-loss messaging remain non-regressed.
10. STEP044 strict compact `BT1` validation remains preserved.
11. STEP045A mesh-wide discovery remains preserved.
12. STEP045B live discovered-node destination selection remains preserved.
13. STEP047 Bluetooth phone-node access boundary remains preserved.
14. No routing-core changes are introduced unless explicitly approved before implementation.

## Next Step

Proceed to STEP046B implementation only after these requirements are accepted. Implementation should inspect ACK paths before editing source and should stay focused on ACK parsing, correlation, timeout state, diagnostics, and UI display behavior.
